# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**nucqcd** ("QCD in nuclei", formerly `physics-code`): a collection of C++ (plus some Fortran) libraries and executables by Wim Cosyn for high-energy reactions on nuclei (JLab to EIC energies), used to learn about the strong force in nuclei. It covers Glauber/RMSGA final-state interactions, quasi-elastic knockout, deuteron and He3 inclusive and tagged DIS, rho/pion transparencies, neutrino QE scattering, and (optionally) deuteron GPDs via PARTONS. A Catch2/CTest test suite lives in `tests/` (see below). The programs in `progs/` serve as both drivers and production calculations. More background is in `manual/manual.tex` (LaTeX) and in the Doxygen comments in the headers. Not everything has Doxygen comments, especially the older code (mostly in `Tools`, e.g. the `Kinematics*`, `Spinor` and `Deuteron` classes). After `make doc`, `build/doxygen_warnings.log` lists what is missing.

## Build

Dependencies: GSL, a Fortran compiler, and CMake ≥ 3.16; ROOT 6 is optional and only used by the test `unit_vectors` (comparison with ROOT's vector classes), which is skipped when ROOT is not found (`-DROOT_ENABLED=no` to build without it; the configure output lists what was skipped). The fit programs use the standalone Minuit2 (see below), not ROOT. `make doc` needs Doxygen, and Graphviz (`dot`) for the class and include graphs; both are optional, and CMake turns the graphs off when `dot` is missing. The code is compiled as C++17 (ROOT 6.40 itself is built with C++23; ROOT's libraries are linked by path so that its C++ standard is not imposed). Release builds use `-O3 -march=native` (no OpenMP: the C/C++ code has no OpenMP directives). LHAPDF and PARTONS are optional (MPI only for two attic programs, see below). LHAPDF (found through its pkg-config file, also in `~/.local`; `-DLHAPDF_ENABLED=no` to skip it) adds the `"LHAPDF:<set>[:<polarized set>]"` structure functions of `NucleonStructure` (`Tools/StructureFunctions/LHAPDFStructure`) and is needed for `"MSTW"` (the set MSTW2008lo68cl; nucqcd no longer bundles the MSTW grid code) and for `PARTONS_ENABLED` (libGPD takes the MSTW PDFs from it). Its tests need the sets CT18LO, NNPDFpol11_100 and MSTW2008lo68cl and are skipped without them. PARTONS v5 (`elementary-utils`, `numa`, `partons`, no longer uses Qt) needs SFML 2.6, LHAPDF, APFEL++, CLN, Eigen3 and libxml2. Ubuntu 26.04 only packages SFML 3, which removed the `sf::Thread`/`sf::Mutex`/`sf::Lock` classes PARTONS uses, so SFML 2.6 is built from source. PARTONS and these dependencies are installed in `~/.local`, which CMake searches automatically when `PARTONS_ENABLED` is set; the PARTONS sources are cloned next to this repo in `~/Git`. LHAPDF is built with its Python bindings (`import lhapdf` from the system `python3`; the module goes to the user site-packages, so a venv only sees it with `--system-site-packages`); PDF sets are installed with `lhapdf install <set>` into `~/.local/share/LHAPDF`. Since 2020 PARTONS has no built-in PDF set: `GPDVGG99` needs its LHAPDF set given as a module parameter (the `progs/GPD` programs call `setSetName("MSTW2008nlo68cl")`), and `GPDMMS13` hard-codes `MSTW2008nlo68cl`; `GPDMMS13` provides only H and E. To set this up on a new machine, run `scripts/install_partons.sh`. PARTONS programs only start with `partons.properties` (and the `logger.properties` it points to) in the executable's directory; the script creates both in `GPD_Partons/bin`, where the `progs/GPD` programs are installed.

```bash
cd build
cmake -DCMAKE_CXX_COMPILER=g++ -DCMAKE_C_COMPILER=gcc -DCMAKE_BUILD_TYPE=Release -DBUILD_PROGS=yes ..
make install -j4          # the VS Code default build task (cwd = build/)
make doc                  # Doxygen API docs -> doc/, warnings -> build/doxygen_warnings.log
```

- `-DBUILD_PROGS=yes`: executables in `progs/` are `EXCLUDE_FROM_ALL` unless this is set. Without it, build one program with `make <target>` (e.g. `make poldeut`), but it is not installed into `bin/`.
- Other options: `-DLHAPDF_ENABLED=no` (LHAPDF is used when found), `-DPARTONS_ENABLED=yes` (builds `GPD_Partons/` and `progs/GPD`), `-DSTATIC_BUILD=yes` (adds `*ST` static libs), and `-DCMAKE_BUILD_TYPE=Debug`.
- `make install` copies shared libs into `<repo>/lib` and executables into `<repo>/bin` (the default `CMAKE_INSTALL_PREFIX` is the repo itself). Binaries use an RPATH that points at `<repo>/lib` plus the directories of linked external libraries (e.g. `/opt/root/lib`, `~/.local/lib`), so run them from `bin/` after installing.
- Cuba is not bundled. `Integrator/CMakeLists.txt` uses an installed Cuba if it finds one (`-DCUBA_ROOT=<prefix>`, `$CUBA_ROOT`, `~/.local`, the system; `scripts/install_cuba.sh [prefix]` installs the patched one into `~/.local`), and otherwise downloads Cuba 4.2.1 (URL and SHA256 pinned; `-DCUBA_TARBALL=<file>` for a local copy, `-DCUBA_DOWNLOAD=yes` to skip an installed one), applies `cmake/patches/cuba-4.2.1-nucqcd.patch` (a Suave bug in Cuba itself, see ROADMAP step 4; a Cuba from elsewhere may lack it, `unit_cuba` catches that) and builds it in the build tree with autotools, serially (`make -j1`) and with `-std=gnu17`, because it does not compile as C23 under gcc ≥ 15. Link the INTERFACE target `cuba` to use it (provides `<Cuba/cuba.h>`, the library and the build dependency); a downloaded `libcuba.a` is also installed into `lib/`. The first configure needs network access unless Cuba is installed or `CUBA_TARBALL` is given.
- cubature is not bundled either (the engine of `numint::cube_adaptive`). `Integrator/CMakeLists.txt` downloads cubature 1.0.4 at configure time (URL and SHA256 pinned; `-DCUBATURE_TARBALL=<file>` uses a local copy of `v1.0.4.tar.gz`), applies `cmake/patches/cubature-1.0.4-nucqcd.patch` (adds `hcubature_minEval`, the minimum number of evaluations of the 2010 `adapt_integrate` that nucqcd bundled before; the rule to choose the dimension to split a region is that of cubature 1.0.4, which changes results of integrands with steps compared to the 2010 code, and `-DCUBATURE_LEGACY_SPLIT=yes` selects the 2010 rule to reproduce results computed before 2026-11 bit for bit, see ROADMAP step 7) and compiles `hcubature.c` into `libIntegrator`; the header is `<cubature/cubature.h>`. A cubature from the system has no `minEval` and is not used. Needs the `patch` program (as Cuba does).
- Minuit2 (for the fit programs in `progs/F2_largex_fit` and `progs/deepsdis`) is the standalone one from the ROOT sources (github.com/GooFit/Minuit2, tag v6-40-02). `cmake/Minuit2.cmake` uses an installed one if it finds it (`-DMINUIT2_ROOT=<prefix>`, `$MINUIT2_ROOT`, `~/.local`, the system; `scripts/install_minuit2.sh [prefix]` installs it into `~/.local`) and otherwise downloads it (SHA256 pinned; `-DMINUIT2_TARBALL=<file>` for a local copy, `-DMINUIT2_DOWNLOAD=yes` to skip an installed one) and builds it in the build tree in a few seconds. A program that links the INTERFACE target `minuit2_libs` is skipped with `-DMINUIT2_ENABLED=no`. The programs use `Fitting/MinuitFitter.hpp` (`nucqcd::MinuitFitter`), which keeps the interface of ROOT's `TFitter` that they used (external parameter numbers, limits `0,0` = none, the old `fcn(npar, gin, f, par, iflag)`, the commands `"MIGRAD"`, `"SIMPLEX"`, `"MINOS"`, ...), see its header for the differences from TMinuit.
- ROOT (optional) is found through its own CMake config (`ROOTConfig.cmake`): source `thisroot.sh` (sets `ROOTSYS`), or it is taken from `/opt/root`. A test that needs it lists `root_libs` in its `LINK`; `nucqcd_add_program(s)` and `nucqcd_add_test` skip it when ROOT is not found (and a program or test that links `minuit2_libs` when Minuit2 is disabled). GSL uses CMake's built-in find module; only the PARTONS libraries (`ElementaryUtils`, `NumA++`, `PARTONS`) use find modules in `GPD_Partons/cmake/Modules`, and SFML its own config.

## Roadmap and where to pick up

`docs/ROADMAP.md` holds the ordered cleanup and modernization plan and its status. **To continue the work, start with its section "Where we are / next up"** (right after the status table): it says what was done last, the recommended next step, and the open choices. Read the ROADMAP before cleanup or refactoring work, and update its status (and that section) in the same PR as the work. `docs/HISTORY.md` records where the code came from (SVN, UGent GitHub, github.com), its contributors, the archived branches, and which programs produced which results.

## Working with the author (agreed workflow)

These rules were agreed in earlier sessions; they are kept here because Claude's memory does not move between computers.

- **One branch and one PR per roadmap item or bug**, opened after the work is done and tested, with the ROADMAP updated in the same PR. A roadmap-only addition requested while a PR is open may go into that PR as a separate commit (say so in the PR description).
- **Merge only when the author says "merge it" (or "merge"; "merge both" for two PRs).** Merge with `gh pr merge <N> --merge --delete-branch`; right after a push GitHub may report the PR as not mergeable yet, so poll `gh pr view <N> --json mergeable` until it is not `UNKNOWN`. Change a PR description with `gh pr edit <N> --body-file file` (works with `gh` 2.106 from GitHub's apt repository; Ubuntu's packaged 2.46 still queries Projects classic and fails with a GraphQL error, then use `gh api -X PATCH repos/wcosyn/nucqcd/pulls/<N> -F body=@file`).
- **Physics value changes need the author's explicit OK.** State them in the PR (which values, by how much, why); "merge it" on such a PR is the OK. Never re-baseline regression references without understanding why they moved, and re-baseline only the entries that the change explains (restore unrelated ones, e.g. last-bit differences).
- **Bugs found along the way** become ROADMAP items (also when nothing was affected: record that) and get their own PR unless the author says otherwise.
- **Before a PR:** build everything (`make install -j8` with `BUILD_PROGS`, and `PARTONS_ENABLED` if installed), `ctest -LE slow`, and `ctest -L slow` for changes that can affect the Glauber code or constants; `make doc` must give no new warnings. PR descriptions must be accurate (test counts, what was and was not checked).
- **Documentation:** Doxygen per class, with paper references where possible (marked for the author to confirm), and every inferred unit or convention flagged in the PR description; the code mixes MeV and GeV and rarely states conventions, and wrong inferred docs are worse than none.
- **Line endings:** LF everywhere (`.gitattributes`: `text=auto eol=lf`). Only five third-party Fortran files keep their original CRLF (`-text` in `.gitattributes`); keep them CRLF when editing with scripts (read and write in binary mode). The commit that converted the C++ files is in `.git-blame-ignore-revs` (`git config blame.ignoreRevsFile .git-blame-ignore-revs` once per clone).
- **A new computer** needs network access for the first configure (Cuba and cubature are downloaded; or `scripts/install_cuba.sh` and `-DCUBATURE_TARBALL`), GSL and a Fortran compiler (Minuit2 is downloaded too, or `scripts/install_minuit2.sh`; ROOT only for `unit_vectors`); for LHAPDF/PARTONS run `scripts/install_partons.sh`, which also installs the LHAPDF sets CT18LO, NNPDFpol11_100, MSTW2008lo68cl and MSTW2008nlo68cl (without the first three the LHAPDF and MSTW tests are skipped, and `"MSTW"` does not work; the last one is the PDF set of the PARTONS models VGG99 and MMS13).

## Tests

`tests/` holds a Catch2 v3 suite, fetched by CMake on the first configure, and is built when `BUILD_TESTING` is ON (the default). Details are in `tests/README.md`.

```bash
cd build && make -j8 && ctest -LE slow -j8    # unit + regression, ~30 s
ctest -L slow                                # Glauber grids computed from scratch
NUCQCD_UPDATE_REFERENCE=1 ctest -L "regression|slow"   # re-baseline, then review git diff tests/reference/
```

- Labels: `unit` (analytic or exact checks), `regression` (golden values in `tests/reference/*.ref`, captured from master on 2026-11-20; the entries that depend on the adaptive integrator were regenerated on 2026-11-26 when cubature was unbundled, see ROADMAP step 7), `slow`.
- A regression failure is a lead to investigate, not a verdict: the old value may itself be wrong. Re-baseline only when the change is understood.
- Tests use a sandbox share dir (`build/tests/share`, with an empty `grids/`) via `nucqcd_test::share_dir()`, never `share/grids/`; the test `main()` unsets `NUCQCD_GRID_DIR`.
- Bugs found by the suite are documented as `[known-bug]` tests (`[!mayfail]`, or hidden `[.]` when they crash).
- Test target names are prefixed `unit_`/`reg_`. `progs/attic/camille/test` already defines `test_*` targets.

## Library layering

Libraries build in this order, and each links against the ones before it:

1. **Integrator** (`libIntegrator`): integration code (Cuba itself is downloaded or installed, see Build). `numint/` provides templated Romberg/trapezoid/Clenshaw-Curtis/Fubini routines. Adaptive cubature (`hcubature` of S. G. Johnson's cubature 1.0.4) is downloaded, patched and compiled into the library at configure time, see Build. `numint/numint2Cuba.hpp` wraps the `numint::mdfunction` functors for Cuba.
2. **Tools**: general physics and math, in four libraries, one per subdirectory, each linking the ones before it (the target **MePhys** is an INTERFACE target that links all four, so programs that link `MePhys` get everything; the names carry a `Tools` prefix because a `libCore.so` would clash with ROOT's):
   - `Tools/Core` (`libToolsCore`): `constants`, `ErrorMessage`, string and math utilities, `GridCache`, `RunLog`, four-vectors, gamma matrices and spinors (`FourVector`, `Matrix`, `GammaStructure`, `LorentzQuaternion`, `Spinor`), `recmosh`, and `nucqcd::Vector2/Vector3/LorentzVector/Rotation/LorentzRotation`, the replacements of ROOT's `TVector3` & co. (same interface and the same results as ROOT; all code uses them since ROADMAP step 9 phase 4b, written as `nucqcd::Vector3` etc.).
   - `Tools/Kinematics` (`libToolsKinematics`): `Kinematics2to2/2to3`, `ElectronKinematics`, `LeptonKinematics`, `LightConeKin*`.
   - `Tools/WaveFunctions` (`libToolsWaveFunctions`, needs Kinematics): deuteron wavefunctions (`Deuteron` plus its parametrizations `YukawaWavefunction`, `GrossWavefunction`, `CstWavefunction`, `InterpolatingWavefunction` behind `WavefunctionImplementation`, and `OldDeuteron`) and `He3wf` (Fortran).
   - `Tools/StructureFunctions` (`libToolsStructureFunctions`, needs Kinematics, not WaveFunctions): nucleon/nuclear structure functions and PDFs (CTEQ, Alekhin, GRSV, mostly Fortran; MSTW and any other set through LHAPDF), `DeuteronStructure`.
3. **Glauber** (`libGlauber`): mean-field nuclei (`MeanFieldNucleus[Thick]`), nucleon EM and weak current operators, `FastParticle` (the ejected particle and its scattering parameters), and the FSI grid hierarchy described below.
4. **Knockout** (`libKnockout`): quasi-elastic A(e,e'p), rho/pion transparency, and neutrino QE cross sections. These are built on Glauber grids. `EMQEHadronCurrent`/`EMQECross` (until 2026-11 `Model`/`Cross`) form the main A(e,e'p) pair, the electromagnetic counterpart of `WeakQEHadronCurrent`/`WeakQECross`.
5. **DIS** (`libDIS`): inclusive and tagged DIS on the deuteron and He3, the polarized deuteron (`Poldeut`), resonances, and the EMT light-front convolution. `DIS/evolution/` is a separate Fortran library, `libEvolution`, for QCD evolution.
6. **GPD_Partons** (`libGPD`, optional): deuteron vector and transversity GPD convolutions that use PARTONS.

All CMakeLists use the helpers in `cmake/NucQCD.cmake`:

- `nucqcd_add_library(<name> SOURCES ... LINK ...)`: shared library (version 1.0.0) with the repository root as public include dir, installed into `lib/`; with `STATIC_BUILD` also `<name>ST`. Dependencies in `LINK` are public, so programs only need to name the highest library they use. Libraries are linked with `--no-undefined` (Linux), so `LINK` must list every library whose symbols are used; a missing one is a link error, not a runtime one.
- `nucqcd_add_program(<name> [SOURCES ...] LINK ... [DESTINATION dir])` and `nucqcd_add_programs(LINK ... PROGRAMS a b c ...)`: executables (default source `<name>.cpp`), built by `make` and installed only with `BUILD_PROGS`.
- Interface targets for external dependencies: `root_libs`, `GSL::gsl`, `cuba`, `partons_libs`. MPI is not used by the libraries: `TMPI` and the two programs that used it (`rhod`, `rhottest`) are in `progs/attic/mpi`, built only when CMake finds MPI. Parallel integrand evaluation comes from Cuba (forked workers on one node, `CUBACORES`).

Programs start `main` with `nucqcd::RunLog runlog(argc, argv, {"name of argv[1]", ...});` (`Tools/Core/RunLog.hpp`): it writes the command line, date, host and build (git describe, flags, library versions) as `# ` comment lines to stdout, and the wall time at the end. The git state is generated into the build tree at every build (`cmake/BuildInfo.cmake`).

**Includes** are written as the path from the repository root, with angle brackets: `#include <Tools/WaveFunctions/Deuteron.hpp>`, `<Glauber/FastParticle.hpp>`, `<Integrator/numint/numint.hpp>` (Cuba stays `<Cuba/cuba.h>`, from the `cuba` target, which `Integrator` links). Headers have the extension `.hpp`. Only headers that belong to one program and sit next to it are included with quotes and without a path.

To add a source file, list it explicitly in that library's `CMakeLists.txt`; there is no globbing. To add a program, add a `nucqcd_add_program(s)` line to the `CMakeLists.txt` of its `progs/` subdirectory (new directories are registered in `progs/CMakeLists.txt`).

## Key cross-cutting conventions

- **`Tools/Core/constants.hpp` is generated** from `Tools/Core/constants.hpp.in` at configure time and is gitignored, so edit the `.in` file. The generated file defines the physical constants as `inline constexpr` variables in namespace `nucqcd` (`nucqcd::mass_p`, `nucqcd::hbarc`, ...; masses in MeV unless the name ends in `_GeV`). The old macro aliases (`MASSP`, `HBARC`, `HOMEDIR`, ...) were removed; only `PI` is left, a literal macro because `Integrator/numint/macros.hpp` defines it too. `nucqcd::share_dir` is the absolute path to `<repo>/share`.
- **The `share/` data directory** holds input data such as nuclear mean-field wavefunctions (`share/input/*.radial*.bound`), PDF grids, and correlation grids. Experiment data used for fits and comparisons (DEEPS, BONuS) are in `share/expdata/`. Most physics classes take a `dir`/`homedir` string argument, usually `nucqcd::share_dir`, and read their input relative to it.
- **The FSI grid hierarchy (Glauber).** `AbstractFsiGrid` (the interface of all grids, with one named interpolation function for each of the eight `GridVariant`s: FSI, SRC, decay, CT and their combinations; a class says which it has in `getGridNumber`) → `AbstractFsiCTGrid` (adds the CT grid) → concrete `GlauberGrid` (→ `OneGlauberGrid`) and `GlauberThickGridCommon` (→ `GlauberGridThick`, `GlauberDecayGridThick`), plus `ROMEAGrid` (directly from `AbstractFsiGrid`) and `ClassGridThick_SCX`. `GlauberGridThick` and `GlauberDecayGridThick` share `GlauberThickGridCommon` (the grid arrays, the loops over the grid points, the cache I/O, the SRC correlator; they differ in the number of variants and in the integral of one grid point). It is single inheritance, no virtual bases. The grid arrays are `Grid3D<T>` (`Tools/Core/Grid3D.hpp`, an owning 3D array with `grid[i][j][k]` indexing) or `std::vector`s of them, not raw pointers. A user adds `FastParticle`s, then calls `fillGrids()`/`updateGrids()`. The grids are expensive to compute, so they are cached as files under `share/grids/` (gitignored), or in `$NUCQCD_GRID_DIR` if that is set, and reused on later runs (`Tools/Core/GridCache.hpp`; files are written atomically via a temporary file and a rename). The file name is the cache key; it bins the particle kinematics (10 MeV in p, 0.1 rad in θ and φ), and `addParticle` moves each particle to the centre of its bin (`FastParticle::gridBinCentre`), so grids do not depend on which kinematics came first. The key does not record the physics, so if you change the physics or the grid parameters, delete the stale grid files.
- **Namespace `nucqcd`.** All classes and functions of Tools, Glauber, Knockout, DIS and GPD_Partons are in `namespace nucqcd` (`Integrator` keeps `numint`). Programs and tests that use them start with `using namespace nucqcd;` after their includes; library code is inside the namespace (new headers: put the `namespace nucqcd {` after the includes and the include guard, and write forward declarations as `namespace nucqcd { class X; }`). `extern "C"` declarations of Fortran routines stay as they are.
- **No ROOT dictionaries.** The `T*` classes in Tools (and `MeanFieldSpinor`) were ROOT classes (`TObject`/`TNamed` bases, `ClassDef`, LinkDef dictionaries); that was removed (roadmap step 9, phase 1), since the code never used ROOT I/O. Since step 9 phase 4b the libraries include no ROOT header at all (vectors are `nucqcd::Vector3` & co., strings `std::string`); since phase 5 they do not link it either. Use the nucqcd types in new code, not ROOT's.
- **Archived code** is in `progs/attic` (built with `BUILD_PROGS` unless its `CMakeLists.txt` says otherwise, not maintained): abandoned programs and classes such as `twonucl` (`DoubleNModel`, `Pair`), `rhodeuteron` (`RhoDeuteron`, `rhodint`), `threeres` (`InclusiveCrossRes`, not built: one stale constructor call stops it compiling, and when that was fixed experimentally its FSI part returned 0, see the ROADMAP open leads), the MPI programs, and `rombergerN.hpp`, the old nested Romberg routine that the libraries no longer use. Do not put new code there.
- Integrands for `numint` are usually written as a struct functor that holds a pointer to the physics object, plus a static `exec` function. Integration precision is passed in as a parameter, and the integrator choice is often an `int` flag on the class.
- **Errors** are exceptions: `std::invalid_argument`, `std::out_of_range`, `std::logic_error` or `std::runtime_error`, with the message built by `nucqcd::ErrorMessage` (`Tools/Core/ErrorMessage.hpp`), e.g. `throw std::out_of_range(nucqcd::ErrorMessage() << "r out of range: " << r);`. Do not call `exit()` in the libraries.
- The code mixes MeV and GeV units (for example `nucqcd::mass_p` versus `nucqcd::mass_p_GeV` in `constants.hpp`), so check which unit a class expects.
- `bin/`, `lib/`, `build/`, and `doc/` are build outputs and are gitignored.
